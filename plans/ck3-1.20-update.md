# Plan: Update tiger to CK3 1.20.1.1

## Context

Upstream tiger (amtep) stopped at CK3 1.19. CK3 1.20 overhauled religion (rites, tenets, holy sites,
clerical regions, holy orders, organizations, puppets, spiritual fulfillment). The user relies on tiger
for their own mods and for the **CK3 Unofficial Patch** (Unop), which fixes real vanilla bugs. So tiger must
stay strict. The xTiger fork (remote `xTiger`) already updated to 1.20.0.4, but it relaxed checks to cut
the number of vanilla errors, removed the other games and added an app and an MCP server. It is used **only as
a reference**. Any piece copied from it is reviewed line by line, and every relaxation is rejected.

Goal: a locally built `ck3-tiger` for CK3 1.20.1.1, on top of upstream `main`, that makes the Unop's
"False positives due to tiger not updated to 1.20.x" section (`ck3-tiger.conf` lines ~613–939)
unnecessary, without relaxing any check.

**Out of scope:** pre-existing tiger false positives, i.e. those already present with tiger 1.19 on CK3 1.19,
including the Unop's regular "False positives" section. Only problems caused by the 1.20 update are fixed.

## Ground rules

- The working copy of this plan is `.claude/plans/ck3-1.20-update.md`, kept out of git. Steps are ticked off there.
- Branch: `adapt/ck3-1.20.1.1` (already created). One commit per step, each reviewable on its own. The
  branch is kept upstream-ready: other games keep compiling, the diff stays minimal. It is pushed to `origin` only when the user asks.
- **Part A: stop after every step** and show what changed, explaining the tiger concepts involved
  (the user is learning tiger). Commit only after the user has reviewed the step.
- Never relax a check because vanilla trips it. A check is changed only with evidence that the game accepts
  the construct: `.info` docs, `script_docs`, consistent vanilla usage that demonstrably works. Otherwise the
  report counts as a vanilla bug.
- When a removed item has a replacement, it moves to the `Removed("1.20", "…")` / `*_REMOVED` tables. It never stays as a live entry.
- Before each commit: `cargo fmt`, `cargo clippy -p ck3-tiger --all-targets`, `cargo test -p tiger-lib`,
  `cargo check -p <game>` for vic3/imperator/eu5/hoi4, **one at a time** (combined = feature unification errors).

## Notes found during the work

- **tiger runs are not deterministic** (found in A4, 2026-10-17): the same binary on vanilla 1.20 gives totals varying by
  ~0.3–1% (e.g. 191,258 / 191,253 / 190,742), and `RAYON_NUM_THREADS=1` doesn't fix it (2 runs: ~2,150 differing
  reports). Biggest visible effect: shared script values narrow `scope:target` in schemes (char|title|culture|faith)
  depending on which caller validates first → groups like "target returns Title but a Character is needed" flip
  between 18 and 135. Pre-existing, out of scope. For C1/C2: compare groups with tolerance, and confirm any
  surprising group difference with a repeat run before attributing it to a change.
- **Determinism experiment** (2026-10-17): `tmp/deterministic-hasher.patch` (fixed-seed ahash `TigerBuildHasher` in
  `src/helpers.rs`, same idea as xTiger's) + `RAYON_NUM_THREADS=1` → byte-identical runs (~30 s vs ~14 s). NOT to be
  committed on this branch. Multi-threaded stays nondeterministic (~1.7%) because of the scripted-item validation cache
  race and the global variable-scope registry; xTiger fixes those too (`ValidationCache` in macros.rs, deferred
  `VariableScopes::finalize`), the latter weakens checks (variables = any scope during validation). Candidate for a
  separate, later change.
